## Glossary (first-use reference)

- **wavCSE**: this repo — a two-stage speech multi-task-learning (MTL) pipeline. Upstream: a frozen WavLM SSL encoder extracts per-layer hidden states, **frame-pools** them (reduces the time axis within each transformer layer to one vector per layer) at extraction time — this happens once, is baked into the `.pt` file, and is NOT swappable downstream without re-extraction (out of scope for this design). Downstream: loads `.pt` embeddings, **layer-pools** them (reduces the transformer-layer axis to one vector per utterance) at training time — this is the only pooling seam this design builds; "pooling seam" below always means layer pooling.
- **mtlkit**: the new top-level package this design builds (sibling to `upstream/`, `downstream/`, `improvements/`). Contains all real logic: task/dataset registry, pooling, heads, trainer, `combine()`, `compose()`, imbalance, and the config-driven experiment/telemetry system. `upstream/` and `downstream/` are rewritten to be thin wrappers over `mtlkit` — see Constraints and Approach B.
- **KS / SI / ER / IC**: the 4 current tasks — Keyword Spotting (Speech Commands, 12 classes), Speaker ID (VoxCeleb1, 1251 classes), Emotion Recognition (IEMOCAP, 4 classes), Intent Classification (Fluent Speech Commands / FSC, 31 classes, currently one flattened label — see below).
- **Task Relation Learning branch** (owned by Kevin, this design's author) = the `improvements/taskrelation/` folder, containing four methods: **MTRL** (Zhang & Yeung 2010) — the one being migrated onto `mtlkit`, see Constraints — **PMR**, **GBC**, and **TSM**, none of which are touched this pass. **Low-Rank branch** (Chehan) = `improvements/lowrank/`. **Task Clustering branch** (Induwara) = `improvements/clustering/`, implemented as **NCMTL**. **Decomposition branch** (Pathumi) = `improvements/decomposition/`, implemented as **FTN**. Seven method names, four owners, four branches — used interchangeably below with this mapping fixed once, here.
- **Mask** (per-sample, per-task): a boolean, 1 if a given sample has ground truth for a given task, else 0. At collation, each task's label entry is set to the loss function's `ignore_index` wherever its mask bit is 0 — the mask and the ignore-index encoding are two different artifacts (mask is boolean; ignore_index is a sentinel written into the label tensor). In the current 4-task setup, membership is disjoint — each sample's source dataset gives it exactly one valid task position (KS *or* SI *or* ER *or* IC). FSC's action/object/location breaks that assumption: all three positions are valid simultaneously for every FSC sample. `mtlkit/tasks.py` exposes the pure validity function (source dataset → task-validity vector); the dataloader's collate function emits `[B, T]` labels (ignore_index where invalid) and `[B, T]` masks; `mtlkit/heads.py` consumes both. The masked-loss mechanism (already used in wavCSE's `trainer_utils.py`) handles both the "exactly one valid task" and "several valid tasks" cases uniformly.
- **Frozen-embedding seam**: the existing `.pt`-file boundary between upstream extraction and downstream training. This already exists in wavCSE and is **not new work** — the framework consumes it as-is at the input boundary; no new module is built for it (see the seam table below).

## Problem Statement

wavCSE's downstream MTL pipeline and its four `improvements/` branches (Task Relation Learning, Low-Rank, Task Clustering, Decomposition) each duplicate the core trainer/model wholesale to add one new idea, because there's no shared abstraction for tasks, datasets, parameter-sharing composition, or loss-combination. The task/dataset conflation (issue #9: `task_type` tokens map 1:1 onto exactly one dataset) also blocks FSC's natural 3-label structure (action/object/location) from being modeled as three heads instead of one flattened 31-class label. The goal is a companion library (`mtlkit`) that makes tasks, datasets, pooling, parameter-sharing composition, loss-combination, imbalance, and config-driven experiment orchestration each a first-class, extensible seam from day one — not competing with PyTorch/TensorFlow, and not disturbing any existing consumer of wavCSE.

**Referenced issues** (already filed, `ready-for-agent`): **#8** cross-cutting utility duplication (label/task/dataset mappings and masked-loss/accuracy functions independently copy-pasted between upstream/downstream and between trainer/evaluator). **#9** task/dataset 1:1 conflation (this design's foundational fix). **#10** no extension point for loss-combination strategies (each new weighting method today means copy-pasting the whole trainer batch-processing method). **#11** dataloader/evaluation performance (eval `batch_size=1`, `num_workers=0`, one small `.pt` file per utterance).

## What Makes This Cool

MTRL (Task Relation Learning branch) is the first proof for `combine()`: its ~85-line duplicated trainer method collapses into one file, dropping the `sys.path.insert` hack it currently uses to reach `downstream/`. FSC's natural 3-label structure (action/object/location) becomes expressible instead of flattened. Every seam — task/dataset registry, pooling, `combine()`, `compose()`, imbalance — is first-class and swappable from day one, described by a declarative experiment spec: one YAML file to run an experiment, with a Python-script escape hatch for anything the YAML can't express, and every run automatically logged to the existing MLflow integration. Composing two parameter-sharing strategies on one shared layer — currently impossible in any existing MTL library, including LibMTL — becomes something you can actually try. And every other existing consumer — PMR, GBC, TSM, Low-Rank, Task Clustering, Decomposition, the base training scripts, the pooling-grid search — keeps running completely unmodified, because `upstream/` and `downstream/` become thin wrappers with the exact same public interface they have today.

## Constraints

- Not competing with PyTorch/TensorFlow — thin companion layer only. Boundary rule: a seam may wrap or replace a named module through its documented interface; the framework never owns the base model's forward pass outside declared seams.
- **Backward compatibility is a hard constraint, not a nice-to-have.** `upstream/` and `downstream/` are rewritten to act exactly as they do today — same public classes, same function signatures, same behavior — but internally delegate to `mtlkit`. Verified exact import surface every other consumer depends on (grepped across all of `improvements/`): `dataset.load_embedding.LoadEmbedding`, `model.downstream_model.DownstreamMultiTaskModel` + `MultiClassifierOutput`, `trainer.trainer_model.MultiTasksModelTrainer`, `trainer.trainer_utils.BatchStats`/`masked_ce_loss`/`masked_accuracy`, `evaluator.evaluator_model.MultiTasksModelEvaluator`, `pooling.pooling.Pooling`, `utils.constant_mapping.LabelKeywordMapping`/`TaskDatasetMapping`, `utils.pooling_id.make_pooling_name`, `utils.load_config.load_config`, `utils.setup_device.set_device`, `utils.setup_logging.setup_logging`, `utils.parse_transformer_layers.parse_transformer_layers`. Every one of these must keep its exact current signature and behavior.
- **Only MTRL is actively migrated onto `mtlkit` this pass.** PMR, GBC, TSM, Low-Rank, Task Clustering (NCMTL), Decomposition (FTN), and the base/pooling-grid scripts are explicitly **out of scope** for migration — no code changes, no dedicated verification effort beyond the general wrapper-compatibility guarantee above. This constraint is orthogonal to Approach B's seam scope: building `compose()`/config-telemetry from day one doesn't mean migrating every branch onto them yet.
- One real user right now (the author); wavCSE is the acceptance test, not a hypothetical future user.
- Tests are in scope for this pass, not deferred: unit tests for every `mtlkit` module (including `compose()` and `experiment.py`), facade-parity tests proving the wrapped `upstream/`/`downstream/` behave identically to today, and an MTRL numeric-parity test.
- **Sanctioned exception to CLAUDE.md's "downstream/ is never edited" rule** (Eng Review D1, decided 2026-09-06): this pass is a documented, deliberate exception — behavior-preserving refactors of `downstream/` are allowed here specifically because they're gated by the facade-parity and numeric-parity test suites (Success Criteria), not left to trust. `CLAUDE.md` must be updated (as an Implementation Task) to record this exception rather than silently overriding the stated rule.
- **`mtlkit` ships as an installed editable package** (Eng Review cross-model tension, decided 2026-09-06): `pyproject.toml`'s `package = false` and the documented `cd downstream && python main.py` invocation mean a repo-root `mtlkit/` sibling is unreachable from `downstream/`'s `sys.path` as currently configured (confirmed: Python puts the script's own directory on `sys.path[0]`, not the repo root). Flip `package = false` to `true` (or otherwise make the project `uv pip install -e .`-able) so `import mtlkit` resolves from any entry point. This is an Implementation Task for Next Step 5, not deferred.

## Premises

1. Differentiated value is the speech-domain layer (task/dataset registry, pooling, imbalance handling, config-driven orchestration) plus a deterministic composition mechanism for stacking parameter-sharing strategies — not reimplementing single-strategy sharing/weighting methods, which stay wrapped as algorithm sources at exactly the loss-combination seam, if/when actually needed.
2. wavCSE is the starting point, not a permanent boundary — "it should do what wavcse to, no need to be exactly around wavcse, but it is the starting point as of now" (verbatim).
3. Task/dataset decoupling (issue #9's many-to-many design) is the foundational abstraction everything else depends on.
4. Stacking/composing multiple parameter-sharing methods on one shared layer is a genuine design question, real enough to build as a first-class seam now — accepting the known risk (see Reviewer Concerns) that no real consumer validates it yet, since MTRL turned out to be loss-level, not parameter-sharing. Built as a deterministic, declared-order mechanism with a synthetic fixture proving the wiring, not a claim that it's validated against a real method.
5. Scope the initial build around wavCSE's existing behavior plus MTRL's migration for the *migration* axis — but every seam (including `compose()` and the config/telemetry system) is built now, not deferred, per the restored Approach B scope.
6. **Every existing consumer of wavCSE keeps working with zero code changes**, verified via facade-parity tests, not just asserted.

## Cross-Model Perspective

Codex's independent cold read: the strongest framing is "a speech-MTL experiment system, not another MTL library" — a thin seam-based core where declaring tasks/datasets/edges and picking one strategy per seam is the only work, with wavCSE ported in as the reference fixture and regression test. Its key quote-callback: *"it should do what wavcse to, no need to be exactly around wavcse, but it is the starting point as of now"* — read as "generalize by extraction, only when a second dataset or task actually demands it." Two rounds of adversarial doc review found MTRL doesn't exercise a composition seam — it's loss-level, not parameter-sharing — which is why `compose()` here is explicitly framed as a wiring-validated-by-fixture seam, not a validated-by-a-real-method one: the risk is known and accepted, not hidden.

## Approaches Considered

### Approach A: Direct Port (minimal viable) — considered, not chosen
Port wavCSE's downstream pipeline through the core modules with 4-task reproduction as the acceptance gate; fixes #8/#9/#10/#11 as a byproduct, but rewrites `upstream/`/`downstream/` in place rather than wrapping, and builds no composition or config/telemetry seam. Rejected: doesn't deliver the full vision.

### Approach C: Config-First, Composition Deferred — considered, tried, not chosen
A narrower cut of this same plan: build only the seams with a proven near-term consumer now (task/dataset registry, pooling, heads, `combine()`), defer `compose()` and the config/telemetry system to a later pass. This was implemented for part of a session, then reverted: the user judged the fuller vision (Approach B) worth building now rather than incrementally, even though `compose()` and the config system don't yet have a validated real consumer — see Premise 4 and Reviewer Concerns for the accepted risk.

### Approach B: Full Seam-Based Framework (all seams from day one) — chosen
Every axis — task/dataset registry (many-to-many), layer pooling, masked heads + model assembly, the trainer's `combine()` hook, a deterministic declared-order `compose()` mechanism for stacking parameter-sharing strategies, imbalance-handling, and a config-driven experiment system (YAML spec + Python-override escape hatch + MLflow-wrapped telemetry) — is built as a first-class, independently extensible seam now. `upstream/`'s and `downstream/`'s existing modules are rewritten as thin wrappers preserving their exact current public interface, delegating internally to `mtlkit`. MTRL is rewritten to import `mtlkit` directly and migrates onto `combine()`; PMR, GBC, TSM, Low-Rank, Task Clustering, Decomposition, and the base/pooling-grid scripts stay untouched, per Constraints.

## Seam → Module → Acceptance Map

| Seam | Module | v1 scope | Validated by |
|---|---|---|---|
| Task/dataset registry | `mtlkit/tasks.py` | Many-to-many, per-(sample,task) boolean masks; absorbs the label/task/dataset mappings currently duplicated between `upstream/utils/` and `downstream/utils/` (closes #8's mapping half) | 4-task parity + FSC 3-head criteria + facade-parity tests |
| Pooling (layer only) | `mtlkit/pooling.py` | Existing downstream layer-pooling strategies moved verbatim, registry-dispatched. Frame pooling stays upstream/frozen (see Glossary), out of scope. | Pooling dispatch-equivalence + new-strategy-run criteria |
| Heads + masked loss + model assembly | `mtlkit/heads.py` | `masked_ce_loss`/`masked_accuracy` unified (closes #8's loss-function half); `build_heads(tasks) -> ModuleList` and `build_trunk()` own assembling the shared trunk + per-task heads into one model | 4-task parity + FSC 3-head criteria |
| Trainer loop | `mtlkit/trainer.py` | Thin loop hosting the `combine()` and `compose()` hooks; not itself a seam | 4-task parity |
| Loss-combination | `mtlkit/combine.py` | Hook (closes #10). Per-step contract: receives per-task masked losses, per-task boolean masks, and each classifier head's **live, autograd-connected** weight/bias tensors (not detached copies — required for backprop); returns one scalar combined loss. Any task-specific repacking of those raw tensors (e.g. MTRL's parameter-matrix transform) is the strategy's own responsibility, not the seam's. Strategy objects are stateful and get epoch-lifecycle hooks (`on_epoch_begin`/`on_epoch_end`) — needed because MTRL's real mechanism has a warmup period, an epoch-scheduled analytic refresh of a stateful `Omega`/`Omega^-1` buffer (owned by the strategy, not the model), and its own per-epoch logging. Default `uniform_average` strategy reproduces the original inlined 1/num_tasks arithmetic exactly (4-task case; see Success Criteria's FSC weighting note for the 6-task case). *(Contract tightened, Eng Review cross-model tension, 2026-09-06.)* | MTRL migration, per-step losses matching pre-migration on pinned batches, full-epoch schedule (warmup + Omega refresh) replayed identically |
| Parameter-sharing composition | `mtlkit/compose.py` | Deterministic declared-order mechanism: strategies apply in a stated order; outputs combine additively or sequentially per the registry entry. v1 validated only by a synthetic fixture strategy (a trivial second strategy wrapping the shared trunk) — no real method (MTRL, Low-Rank, or otherwise) validates it yet; see Reviewer Concerns. Scope reaffirmed as-is after Eng Review cross-model tension (2026-09-06): output-space combination only, not broadened to weight-space/objective-space composition speculatively. | Composition wiring criterion (fixture only) |
| Imbalance handling | `mtlkit/imbalance.py` | Per-task class reweighting (e.g. inverse-frequency) inside the masked loss | Imbalance success criterion |
| Config + telemetry + override | `mtlkit/experiment.py` | **Revised (Eng Review decision 1B, 2026-09-06):** Hydra owns YAML composition, CLI/script overrides, and structured-config validation; `mtlkit/experiment.py` becomes a thin adapter mapping the resolved Hydra config into the typed object the trainer consumes, plus the MLflow-wrapped telemetry (no off-the-shelf equivalent tied to the existing run-naming convention) | Config-driven-run success criterion + config error-path test |
| Frozen-embedding seam | *(none — pre-existing)* | wavCSE's `.pt` contract, consumed as-is | N/A — out of scope, not new work |
| `upstream/`/`downstream/` compatibility wrapper | existing files, rewritten internals only | Every symbol in the Constraints import-surface list keeps its exact signature and behavior | Facade-parity test suite (below) |
| Shared strategy registry | `mtlkit/registry.py` | **New (Eng Review decision 3B, 2026-09-06):** one generic `Registry[T]` (register/get/list, `KeyError` with valid-keys list on miss), used by all four registry-backed seams (tasks, pooling, combine, compose) instead of four independent implementations | Registry unit tests (Next Step 1) |

## Recommended Approach

Approach B, restored as chosen. `mtlkit` holds every seam — including `compose()` and the config/telemetry system — as first-class from day one; `upstream/`/`downstream/` become compatibility wrappers; only MTRL is actively migrated; every other consumer is verified, not just assumed, to keep working unmodified. The accepted risk (see Premise 4, Reviewer Concerns): `compose()` and parts of the config system are built without a validated real consumer yet.

## Open Questions

- **Wrapper granularity for `LoadEmbedding`**: since the task/dataset registry now supports many-to-many, does the wrapped `LoadEmbedding.load_embedding(task_type, ...)` need a new optional parameter to opt into FSC-as-3-heads, or does that require a new `task_type` composition string only, with no signature change? Resolve during Next Step 1.
- **`compose()`'s combine op default**: for two strategies on one shared layer, what's the exact combine op (additive vs. sequential wrapping) when the registry doesn't specify one explicitly — needs a stated default, informed by whichever real method eventually validates the seam (Low-Rank is the likely first candidate; GBC, an in-branch parameter-sharing method — a shared global bias across heads — is a nearer-term candidate than Low-Rank).
- **Python-override interface shape**: the config system assumes a mutable typed config object; the exact schema (dataclass vs. dict-like) needs a short design pass during Next Step 4 (below).
- **Migration order for the other branches**: PMR, GBC, TSM, Low-Rank, Task Clustering, and Decomposition stay on their current forked trainers indefinitely, per Constraints — no committed migration order because none is planned this pass.

## Success Criteria

- wavCSE's current 4-task (KS/SI/ER/IC) run reproduces its existing per-task dev accuracies through the new core, seed and data order pinned, within a documented small tolerance (e.g. ±0.1pp) to account for floating-point reordering from the refactor.
- FSC-as-3-heads trains jointly with KS/SI/ER (a 6-task run) and reports per-head accuracy plus a joint exact-match metric, compared against the 4-task flattened-IC baseline under an identical upstream encoder, trunk, and optimizer. **Known limitation (Eng Review D2, decided 2026-09-06, accepted as-is):** the default `combine()` weighting is uniform `1/num_tasks` per task-slot, not per valid-task-per-sample — an FSC sample contributes 3× the per-sample gradient weight of a KS/SI/ER sample (3/6 vs 1/6) that an IC sample didn't get in the 4-task baseline (1/4). This is a real confound in the 6-task-vs-4-task comparison, documented here rather than fixed this pass.
- Pooling seam: dispatch equivalence (today's strategy through the registry reproduces parity) and a new-strategy run (trains end-to-end, no parity expectation).
- Imbalance seam, mechanical gate: class-reweighted masked loss reproduces a hand-computed reference value on a pinned batch, **and** — pinned per Eng Review decision 4B (2026-09-06) — on that same batch, the under-represented class's head gradient norm (or loss contribution) with reweighting is ≥1.5× its value without reweighting. Replaces the previously qualitative "gradients demonstrably shift" with a single deterministic inequality.
- **Composition seam (wiring only)**: the fixture second strategy stacks with the existing shared trunk via declared-order composition and trains without shape/gradient errors on the 4-task setup — proves the mechanism is wired correctly, not that any real method benefits from it.
- **Config-driven run**: a full experiment runs end-to-end from a YAML config file alone, with a run automatically appearing in the existing MLflow tracking under the run-naming convention `improvements/` already uses; the Python-override escape hatch successfully overrides at least one YAML-expressed field in a test.
- **Facade parity**: for every symbol in the Constraints import-surface list, a test constructs it through the wrapped `upstream`/`downstream` path and asserts identical behavior to a reference captured from today's pre-refactor code (same inputs → same outputs, same attribute names, same exceptions on bad input).
- **PMR, GBC, TSM, NCMTL, and FTN's existing entrypoints run without modification** against the wrapped `downstream/`/`upstream/` — verified by importing and instantiating each branch's model/trainer subclass against the new wrapper and confirming no import error, no signature mismatch, and (where a synthetic-data smoke run is feasible without real audio) a successful forward+backward pass.
- MTRL migrates to the `combine()` seam and its per-task losses numerically match its pre-migration results on a set of pinned batches, before its duplicated `_process_batch` method is deleted (not kept as a fallback).
- Test suite passes: `mtlkit` unit tests (every module, including `compose()` and `experiment.py`), facade-parity tests, and the MTRL migration test, all runnable via `python -m unittest` following the existing `improvements/clustering/tests/test_ncmtl.py` convention (no new test-runner dependency).
- **Config error path**: a malformed config or an override that doesn't resolve to a real key raises a clear, actionable error before training starts, not a stack trace deep inside the trainer (Eng Review decision 5A, 2026-09-06) — one negative-path test in `mtlkit/experiment.py`'s suite.
- Issues #8, #9, #10, #11 close as a direct consequence of this build.

## Reviewer Concerns

Carried forward from prior review rounds (Approach B scored 6/10, 6/10 in its first attempt; a fixed-up version scored 7/10; Approach C's narrower cut also scored 7/10 before being reverted in favor of restoring this fuller plan):

- **`compose()` is built without a validated real consumer.** Declared-order composition (combining forward-pass outputs of one shared layer) is this seam's shape; MTRL's actual mechanism (loss-level regularizer, confirmed from its source) doesn't exercise it at all, and whether Low-Rank's or GBC's actual parameter-sharing mechanism fits this shape, or needs something else entirely (a weight-space or objective-level transform), is unknown until a real migration is attempted. This is a knowingly accepted risk (Premise 4), not an oversight — the fixture-only success criterion reflects that honestly.
- **LibMTL/TorchJD adapter integration cost is likely underestimated** if ever built: LibMTL implements weighting algorithms inside its own trainer/model wrappers, so consuming its math without its trainer may mean reimplementing rather than wrapping. Do a short spike before committing to either library if a GradNorm/FAMO-class experiment is ever planned.
- **Parity-gate noise floor is undefined.** A pinned seed doesn't guarantee zero run-to-run variance (non-deterministic GPU kernels, small dev sets like ER's 4 classes where 0.1pp is a fraction of one sample). Before Next Step 3's gate is evaluated, measure the current code's own cross-run noise floor under the pinned seed and set the effective tolerance to whichever is larger, ±0.1pp or that noise floor.
- **Reference numbers for the parity gate need to be established under the pinned seed first** — if today's recorded 4-task accuracies weren't produced under a pinned seed/data order, re-run the current (pre-refactor) code once under the pinned configuration to generate the actual comparison target, before Next Step 3.
- **FSC label-provenance mechanics are real but left to implementation**: FSC's per-field (action/object/location) class sets, including the "none" sentinel already used by the flattened label today, need to be derived from the same FSC metadata `load_embedding.py` already reads. Doesn't block this build; resolved during Next Step 8.
- **Full smoke-run verification for PMR/GBC/TSM/NCMTL/FTN may be limited by available test fixtures** — without real audio/embedding data, verification is import + instantiation + synthetic-data forward/backward pass (matching `test_ncmtl.py`'s existing approach), not a full training run reproducing real numbers. Accepted as sufficient since none of these branches are being modified.
- **Config schema and Python-override interface aren't pinned yet** — both need a short design pass at Next Step 4, not discovered mid-implementation.
